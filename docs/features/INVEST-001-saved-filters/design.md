# INVEST-001: сохранённые фильтры - устройство

Правила - в [business-rules.md](../../business-rules.md#сохранённые-фильтры); здесь - где что живёт и почему так.

## Данные

| Таблица | Что |
| ------- | --- |
| `saved_filter` | фильтр: пользователь, название (уникальный индекс `(user_id, lower(name))`), вид, параметры - `BondParametersRequestModel` в JSON (`text`) |
| `bond_alert.filter_id` | правило `SAVED_FILTER` ссылается на фильтр (`on delete cascade`, одно на фильтр - частичный уникальный индекс) |
| `saved_filter_match` | выборка прошлой проверки: `filter_id`, `uid`, тикер, когда вошла; уникальна по `(filter_id, uid)`, удаляется с фильтром |

Параметры хранятся JSON, а не колонками: фильтров скринера много и они ещё добавляются (этап 10), а читаются
параметры только целиком - для выборки и для UI. Пишется модель без `batchLimit`; читает её тот же
`BondParametersMapper`, что запрос страницы, - выборка фильтра совпадает с тем, что пользователь видит в таблице.

## Код

| Что | Где |
| --- | --- |
| CRUD фильтров, переключатель уведомлений | `SavedFilterUseCaseImpl` (alert-service) |
| JSON параметров и выборка по ним (`BondUseCase.getAllFiltered`) | `SavedFilterParameters` |
| проверка правил `SAVED_FILTER` | `FilterAlertCheckUseCaseImpl`; вызывает `PriceAlertListener` после `PricesSyncedEvent`, а также включение уведомлений и новые параметры (отправная точка) |
| запас у границ | `FilterMargins.loosen` |
| текст уведомления | `AlertTexts.filter` |
| REST | `SavedFilterController` (`/internal/rest/alerts/filters`), `SavedFilterDtoMapper`; DTO - `ru.invest.api.dto.filter` |
| лимит `SAVED_FILTERS` | `PlanLimit`, `EntitlementUseCaseImpl` (текст `402`), `AccountPlanUseCaseImpl` (использование) |

## Решения

- **Правило - строка `bond_alert`, а не флаг у фильтра.** Так даром работают очередь и её `dedup_key`, история со
  ссылкой на правило, кнопка «Отключить это уведомление» в Telegram (`alert-off:<id>`), `/list` бота и лимит правил.
  Отключённое в Telegram правило остаётся (`notify: false`, `alertId` есть); выключение в UI удаляет правило - оно
  перестаёт занимать лимит. Создавать его через `POST /alerts` нельзя: у правила нет параметров, кроме фильтра.
- **Отправная точка - `state`.** `ARMED` - выборка запомнена; `null` - запомнить при ближайшей проверке и ничего не
  слать. Включение, повторное включение и новые параметры сбрасывают `state` и сразу проверяют правило. Пока кэш
  облигаций пуст (старт приложения), проверка ничего не делает: пустая выборка как отправная точка дала бы потом
  уведомление обо всех облигациях сразу.
- **Одно уведомление на проверку, а не на облигацию.** Широкий фильтр после первой загрузки свечей или рейтингов
  может «впустить» десятки облигаций - это одно сообщение со списком. Ключ - `SAVED_FILTER:<правило>:<номер срабатывания>`,
  как у порогов цены.
- **Запас у границ - вторая выборка с расширенными диапазонами.** Облигация из прошлой выборки остаётся в ней, пока
  проходит расширенный фильтр. Это тот же гистерезис, что у порогов цены (0,2 п.п. цены, 0,1 п.п. доходности), но
  на уровне выборки: не нужно хранить состояние каждой границы.
- **Путь `/alerts/filters`.** Фильтр - личные данные пользователя; под `/bonds/**` gateway пускает гостя, а эндпоинты
  облигаций не должны зависеть от пользователя. `/api/alerts/**` уже проходит через gateway с `X-User-Id` - новый
  маршрут не нужен.

Отвергнуто:

- уведомление на каждую новую облигацию отдельным сообщением - поток при широком фильтре;
- хранить в `saved_filter_match` только «уже уведомлённые» без удаления - облигация, вышедшая из выборки надолго и
  вернувшаяся через месяц, не дала бы уведомления;
- проверка ещё и после загрузки ленты (рейтинги) - цены в торговые часы обновляются раз в 15 минут, задержка
  небольшая, а второй источник срабатываний усложнил бы порядок проверок.
