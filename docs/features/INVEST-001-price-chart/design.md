# INVEST-001: график цены - как сделано

## Данные

`price_candle`: `bond_id` (FK с `on delete cascade` - в сущности `Bond` связи нет, чтобы не грузить свечи вместе
с облигацией), `uid`, `candle_date date`, `open/high/low/close numeric(19,4)`, `volume bigint`, `created_*`.
Уникальный индекс `(uid, candle_date)` - он же индекс для чтения по периоду.

Объём: ~1600 облигаций × ~250 торговых дней × несколько лет ≈ 1-2 млн строк, 100-200 МБ - обычной таблицы хватает.

## Загрузка

| Класс                          | Что                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------- |
| `TinkoffCandleProviderImpl`    | `GetCandles` окнами по 5 лет (лимит API для дня - 6 лет и 2400 свечей): `getDailyCandles(from, to)` и `getDailyHistory(to)` - назад, пока окно не пустое, не больше 30 лет |
| `TinkoffCandleUseCaseImpl`     | `replaceFrom`: удаляет свечи с даты первой новой и вставляет новые (flush между ними - иначе уникальный индекс) |
| `TinkoffCandleSyncUseCaseImpl` | облигации по одной: нет свечей - вся история, есть - с последней даты включительно    |
| `BondDataSyncScheduler`        | шаг `candle` после `price`, флаг `sync.steps.candle` (по умолчанию `true`)             |

Запрос - только биржевые свечи (`CANDLE_SOURCE_EXCHANGE`) **без** `limit`: вместе они дают `INVALID_ARGUMENT 30220`
(«candle_type not supported when limit specified»). На первом запуске на стенде из-за этого упали все 1612 облигаций.

Ошибки API по облигации пишутся одной строкой с кодом и trackingId: стектрейс на каждую облигацию за пару минут
набил 20 МБ, и лог пода ротировался. Если открылся предохранитель SDK (`CallNotPermittedException` после серии
ошибок), шаг останавливается - остальные облигации упали бы так же; их свечи доберёт следующий запуск.
`syncByTicker` при ошибке бросает исключение, чтобы ручной запуск по одной облигации не отвечал «успешно».

Второй прогон на стенде упал по памяти: ручной `sync-all` шёл в HTTP-запросе, а с `open-in-view` по умолчанию
EntityManager жил весь запрос и копил все сохранённые свечи (366 тысяч к моменту `OOMKilled`). Выключили
`open-in-view`, а все `sync-all` теперь идут в фоне (`MaintenanceTaskRunner`, 202 / 409).

`GetCandles` получил свой лимит `invest.rate-limiter.candles` (5 в секунду) - иначе он попадал под общий
лимит 1 в секунду, и ночной шаг шёл бы ~30 минут.

Глубину истории в API заранее не проверяли: поиск назад до пустого окна от неё не зависит. Пустое окно в середине
истории (долгий перерыв в торгах) остановит поиск раньше - для облигаций это маловероятно.

## Чтение

`BondUseCase.getCandles` → `TinkoffCandleUseCase.find` (дневные из БД) → `CandleAggregationUseCaseImpl` (неделя,
месяц - чистая функция). DTO - `invest-api-dto` `bond/candle/CandleDto`, `CandleIntervalDto`; клиент стартера -
`InvestApiBondClient.getCandles` (даты с `@DateTimeFormat(iso = DATE)`: без него Feign отправлял дату в локали JVM).

## UI

`components/BondPriceChart.tsx` в карточке облигации: `AreaChart` из `@mantine/charts` (recharts уже в проекте),
ось Y от минимума к максимуму - неликвидные облигации ходят в узком коридоре. Период → дата `from`
(`lib/dates.periodStart`, в коротком месяце - его последний день). Японские свечи не рисуем: для облигаций
линии достаточно, а `lightweight-charts` - новая зависимость.
